# 10 文本读取-编码探测与分块流式

`read-text` 端点的设计：字节层面分块 + 每块独立解码，客户端滚动续载。
全链路只读、工作区锁定（路径不得越出 root）。

## 编码探测（每次读都重探，4–8 字节 peek）

1. BOM 判定：`EF BB BF` → UTF-8；`FF FE` → UTF-16LE；`FE FF` → UTF-16BE
2. 无 BOM → 先按 **严格 UTF-8**（`TextDecoder('utf-8', { fatal: true })`）
   解码；失败 → **GBK 回退**（iconv-lite，国内遗留文件主战场）
3. 返回实际用的编码标签（`encoding: 'UTF-8' | 'UTF-16LE' | 'UTF-16BE' | 'GBK'`），
   客户端头部显示"编码 · 大小 · 部分"
4. WHATWG TextDecoder 自动剥 BOM；GBK 用 iconv 解码

## 分块

- `offset`（字节）/ `limit`（字节）参数；默认 256KB/块，上限 1MB（clamp）
- **UTF-16 偏移对齐到偶数**（`offset - (offset % 2)`），防半码字
- 响应 `{ size, offset, bytes, content, encoding, lineCount, truncated, binary }`：
  `bytes` 是实际读到的字节数（EOF 截断），`truncated` 驱动客户端续载
- 行数语义：**尾随换行闭合最后一行**（`'a\nb\n'` = 2 行，不是 3）
- 二进制嗅探：首块前 8KB 含 NUL → `binary: true`，客户端显示提示不渲染

## 客户端流式（滚动到底自动续载，绝不抢位置）

- 滚动容器 `onScroll`：距底 <120px 且 truncated 且非加载中 → 拉下一块
- **位置保持**：追加内容在视口下方，浏览器天然保持 scrollTop——可见行纹丝
  不动；**绝不强制钉底**（曾经的 `scrollTop = scrollHeight` 会把"几百行"
  直接拽到文件尾，且链式加载期间上滚也会被拽回——用户实测事故）
- **链式续载只属于"精确贴底"**（距底 <2px）：贴底的用户连续流式（每次
  追加后重钉到新底），一上滚立即退出；中途滚动到块尾只加载一块，加载完
  距新底超过阈值 → 链自动断，继续滚才续——"滚动到极限时查询更多"的渐进语义
- 短内容（比视口矮）视为贴底：自动链到读完（scroll 事件不会触发，由
  layout effect 兜底）
- **追加式 DOM**：plain 用单 pre + 文本节点命令式追加（React 从不重写旧
  文本，每块插入 O(1) 级，替代"整体重写 1MB 文本"的卡顿）；code 每块一个
  独立 Shiki 块，只高亮自己（总成本线性，替代"每次追加全量重高亮"的
  O(n²)），行号计数器放共享容器上跨块连续
- 竞态守卫：`pathRef` 记录当前文件，在途响应回来时路径不匹配直接丢弃
  （快速切换文件不会把 A 的分块追加进 B 的表面）；单飞锁 `loadingRef`
- **无预览上限**（2026-09 移除 2MB 上限）：超大文件滚动分块看全，内存随
  已加载内容增长；首块 256KB 照旧，无限续载直到 truncated=false

## 已知边界（写进 README 的已知限制）

- **块边界对齐（已修复，2026-09）**：曾经"块边界切断多字节字符 → 整块
  误判 GBK 全乱"——现在 decodeChunkBytes 阶梯：严格 UTF-8 整块 → 按
  UTF-8 裁剪块尾重试 → 才判 GBK（按 GBK 规则裁剪）；BOM/提示的权威编码
  直接按它裁剪。裁剪掉的半个字符由下一块按 offset 重读，无损拼接；
  EOF 不裁剪。**裁剪必须用真实编码**：先解码拿真实编码再裁，或按阶梯
  重试——用暂定 UTF-8 裁 GBK 块会把合法的 trail 字节裁掉（踩过）
- **编码稳定性**：客户端把首块探测出的编码随后续请求带回（hint），杜绝
  "恰好是合法 UTF-8 的 GBK 块"中途翻回 UTF-8
- 无 BOM 的 UTF-16 无法识别（按 GBK 回退 → 乱码）
- 多行结构（C 块注释）跨块时按块独立高亮会不完整
