# 12 提交规范与工作流

三个插件仓库统一的提交规范（README 第二节有完整版，这里是要点与动机）。

## 格式

```
<type>: <中文摘要>

1. <要点一>
2. <要点二>
3. <要点三>
```

- 标题一行、动词开头、≤50 字；正文空一行后接**有序列表** 3～5 条，
  总结关键要点不赘述
- type 枚举：`feat` 新功能 / `fix` 修复 / `refactor` 重构 / `docs` 文档 /
  `test` 测试 / `chore` 构建依赖杂项

## 为什么用 -m 数组而不是 heredoc

Windows 控制台是 **GBK**，heredoc（`git commit -F -` 多行输入）会把 UTF-8
中文消息写坏；`git commit -m "标题" -m "1. ..." -m "2. ..."` 每个 -m 一段，
多段自动空行拼接成正文——中文安全。

```powershell
git commit -m "feat: 文件区改为单棵懒加载文件树" -m "1. 根层级自动加载，展开目录按需取层" -m "2. 2s 轮询原地刷新，合并保留展开状态"
```

## 提交切分习惯

- 一个逻辑变更一个提交：`fix:`（缺陷修复）与 `feat:`（新功能）分开，
  即使同一次迭代完成（如"pathspec 修复"与"树重构"同批交付 → 两个提交）
- 提交前 `git status --porcelain` 确认只含目标文件；`git add` 指定文件
- 工作树必须干净才算一轮完成（`lib/`、`node_modules/` 由 .gitignore 排除）
- 初始提交也走规范（`feat: xxx 插件` + 5 条要点，24 文件 6567 行那次）

## 发布节奏与提交的对应

测试版迭代（用户视觉验证）→ 提交 → 用户确认 → 正式版发布（05）。提交
先于视觉验证也 OK（fileexplorer 树重构即先提交后验证）；用户要求改则
追加新提交，不 rewrite 历史。
