# 09 文本查看器-懒加载渲染包

文本查看器的渲染栈（Shiki 高亮 + react-markdown）直接打包进 client.js 会
把启动主包从 45KB 撑到 3.5MB。解法：**拆成独立懒加载 bundle**，首次打开
文件才拉取——启动加载只付出 chrome 的代价。

## 方案

```
src/client/renderer.tsx      # 重代码入口（Shiki 语法 + markdown 管线）
   ↓ tsdown 第三入口          # format cjs, 仅 react 两个模块 external
lib/renderer.js (3.4MB)      # 标准 CJS 模块，随包发布（files: lib/**）
   ↓ host 端点               # readRenderer 读同目录文件（import.meta.url）
POST /textviewer/renderer    # 返回源码字符串（一次拉取，客户端缓存）
   ↓ 客户端包装求值
new Function('module','exports','require', code + ';return module.exports;')
   ↓ require shim            # 'react'/'react/jsx-runtime' → shell 注入的模块
RendererExports              # { getHighlighter, HighlightedCode, MarkdownView }
```

- 渲染包失败自动**降级纯文本**（`rendererFailed` → 显示 error 行 + plain
  pre），绝不白屏；渲染包加载期间显示"读取中"
- 组件接口走 `RendererExports` 纯类型契约（`renderer-contract.ts`，type-only
  双面共用，主包不引入重代码）

## tsdown 的坑（真实验证过）

| 写法 | 结果 |
|---|---|
| banner 用箭头函数/函数声明 `(React) => {` + footer `return ...; }` | **输出 0 字节**（内容全进 sourcemap）——rolldown 对 banner 的顶层语句形态敏感 |
| banner 注释 + 非空 footer | 同样 0 字节（顶层 `return` 非法） |
| 无 banner/footer 的标准 CJS + 客户端 `new Function('module','exports','require', ...)` 包装 | ✅ 3.4MB 正常（Function 体内顶层 return 合法） |
| client 入口同款 banner 能工作 | 因为 banner 开了工厂函数作用域、footer 的 return 在函数内——但渲染包要自持 module/exports，形态不同 |

结论：**懒包用标准 CJS 输出，包装逻辑全放客户端**；require shim 只认
react 两模块，其余（如 `node:process`，某些库会引用）**兜底走主包自己的
require**（loader 的模块表已含）。

## 渲染器注册表（按扩展名分派）

- `EXT_LANGS`（扩展名 → shiki lang id）+ `BASENAME_LANGS`（Dockerfile 等）
- `rendererFor(name)`：`md/markdown/mdx` → markdown；命中 lang → code；
  其余 → plain（不换行横向滚动）
- Shiki 用 `createHighlighterCore` + `createJavaScriptRegexEngine`（**免
  WASM**）+ 精选语言子路径导入（`@shikijs/langs/cpp` 等，v4 导出的是
  相关语法**数组**，需 `.flat()`）；`codeToHtml` 输出 `<span class="line">`
  + 内联 token 色 → 行号用 CSS 计数器（`.line::before { counter-increment }`）
- 高亮重算时**保留旧 HTML**（内容分块增长时表面不闪纯文本）
- v4 语言包大：cpp 521KB、ts/tsx/jsx 各 ~180KB——必须走懒加载，这是
  拆包的动机

## 高亮搬进 Web Worker（2026-09，主线程零阻塞）

Shiki 的 JS 正则引擎**同步**编译/分词：语言首次使用 100–600ms、200KB 块
~1.7s——全压主线程就是"txt 切代码卡顿"的真相。修法：worker 里跑整个渲染
包（fetch 同一 RPC 端点 → new Function 求值 → getHighlighter → codeToHtml），
主线程只收 HTML。

- **worker 引导脚本是 Blob 字符串**：不能 import——react 用空桩（组件从不在
  worker 渲染，只调 getHighlighter）、node 内建用与 renderer-loader 相同的
  桩（**双份维护，注释标明**）
- worker 的 fetch 同源带 cookie，直接 POST `/textviewer/renderer` 信封即可
- 失败即降级：worker 创建/求值失败 → 主线程渲染包高亮器兜底（慢但可用）
- **预暖**：挂载后后台预热常用语言（js/cpp/ts/yaml/json/md），常见格式
  首开即现；冷门格式首开在 worker 里编译，UI 也不冻
- 主题只影响 token 颜色，预暖用挂载时主题即可

## 注意点

- 语言选择与高亮是纯客户端逻辑，host 只管字节与解码（见 10）
- `.ts` 写 JSX 报"未终止正则"——渲染包入口必须是 `.tsx`
- 渲染包 CSS Modules 与主包同 id → 注入去重守卫（dataset.pluginCss 检查）
  保证不重复注入样式
