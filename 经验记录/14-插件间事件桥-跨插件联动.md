# 14 插件间事件桥-跨插件联动

两个插件协作的官方正道是 **cordis 事件总线**（同一页面共享），不是插件间
RPC。案例：ui-cw-fileexplorer 点击文件行 → ui-cw-textviewer 接收并查看。

## 架构决策：纯查看器不重复造轮子

textviewer v1 先实现了自带文件树（`list` 端点 + FileTree 组件），用户指出：
**文件列表 fileexplorer 已经有了，不该每个插件都造一份**。重构为纯查看器：

- textviewer 删除 list 端点（host 与客户端）、删除 FileTree 组件——主包
  从 45KB 降到 32KB
- 文件打开 = fileexplorer 点击文件行 → 事件广播 → textviewer 订阅接收
- 事件载荷携带 `{ name, path, root }`：`root` 是发出方的工作区根，
  接收方直接用它做 read-text 的作用域——**接收方连会话跟随都不需要**

## cordis 上下文过滤（关键机制，踩过才知道）

- 每个插件 client 是独立 fiber（子 ctx），`ctx.plugin` 加载
- `ctx.emit` 从发出者作用域**向上冒泡**；监听匹配条件是"监听者 ctx 是
  发出者的祖先"（EventsService.dispatch 的 context filter）
- **兄弟作用域互不可见**：A 插件的 emit，B 插件在自己 ctx 上 `ctx.on`
  永远收不到
- 接收方两个解法（任一）：
  - `ctx.root.on(EVENT, handler)`——root 是所有 ctx 的祖先（推荐，语义明确）
  - `ctx.on(EVENT, handler, { global: true })`——绕过过滤（保底手段）

## 协议与实现要点

```ts
// 事件名（字符串常量，双端各自定义副本；d.ts 里增强 Events 接口才能过类型检查）
export const FILE_OPEN_EVENT = 'ui-cw/fileexplorer/file-open'
declare module '@deepseek-ai/cordis' {
  interface Events { [FILE_OPEN_EVENT]: (file: { name: string; path: string; root: string }) => void }
}

// 发出方（fileexplorer）：inject 面暴露 notifyFileOpen，apply 里包 ctx.emit
inject: () => ({ ..., notifyFileOpen: (file) => { ctx.emit(FILE_OPEN_EVENT, file) } })

// 接收方（textviewer）：root 订阅 → 组件经 inject 面的 subscribeOpen 挂钩
ctx.root.on(FILE_OPEN_EVENT, (file) => { for (const cb of openListeners) cb(file) })
```

- **组件不碰 ctx**：apply 世界持有监听器集合，inject 面暴露
  `subscribeOpen(cb): () => void`，组件 useEffect 订阅/退订
- 订阅回调用 ref 转发（`openHandlerRef.current = handler`），避免注入面
  身份变化导致反复重订阅
- 重复打开同一文件（重复点击同一行）应跳过重载：记录 lastOpen 的
  {root, path} 去重
- 事件名要命名空间化（`ui-cw/...` 前缀）防碰撞；载荷字段 camelCase，
  绝对路径，接收方不再自行解析
- 无监听者时 emit 是无害 no-op：发出方不需要探测接收方是否存在

## 教训

- 第一版把 fileexplorer 的树照抄进 textviewer：代码重复 + 两棵树各自轮询
  两份 list 实现——用户直接否掉。**先问"这个能力别的插件有没有"，再动手**
- 事件语义（ctx 过滤方向）不能靠猜：读 cordis lib 源码确认（dispatch 的
  filter 逻辑），再定接收方式
